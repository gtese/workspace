# TraceWork

**TraceWork** —— 面向**工程师、财务、人事**三类角色的科研项目职能支持平台，把研发工时填报与
研发费用备查资料两套能力深度融合在同一套系统、同一套 AD 账号体系下。

| 源码仓库 | <https://git.tri.local/it/tracework.git> |
| 部署主机 | `trivm122.tri.local` (172.16.50.122) |
| 版本 | 4.0.0 |
| 技术栈 | Node.js 20 + Fastify + PostgreSQL 16 + Vue 3 + nginx |
| 认证 | Active Directory（LDAP bind，不保存用户密码） |
| 证书 | `*.tri.local` 通配证书（有效期至 2028-10-21） |

**API Key**（推荐给系统集成）：在「系统管理 → 开放 API 密钥」创建，

共 18 个权限范围（`timesheet:read`、`project:write`、`costing:*` 等）。

## 一、平台解决什么问题

研发费用管理在多数企业是**三拨人各管一段、数据对不上**：

- **工程师**按月填工时，为了让财务能算人工费用
- **财务**要把工时折算成钱，归集六类费用，应对加计扣除与高企认定
- **人事**要维护研发人员名册，证明科技人员占比达标

过去这三段靠 Excel 和邮件来回传，月底对账靠人肉。本平台把它做成**一条数据链**：

```
工程师填工时 ──▶ 项目负责人审批 ──▶ 财务一键折算人工费用
                                          │
                                          ▼
人事维护名册/薪酬 ──────────────▶  研发费用辅助账（六类归集）
                                          │
                                          ▼
                              多口径测算（加计扣除/高企/会计/R&D统计）
                                          │
                                          ▼
                              25 份备查资料一键生成 Word
```

**关键点：工时填一次，后面的钱、表、申报材料全部自动出来。**

## 三、核心能力详解

### 3.1 四套口径测算（已与权威实现逐项对账）

平台的测算法则严格依据现行税收与认定规则实现，并**与用户提供的
《研发费用备查资料智能工作台》模板算法做过逐项数值对账**——
用模板自带的示例数据跑两套引擎，22 项指标（六类费用、限额、委托研发、
四口径、六大高企指标）结果完全一致。

| 口径 | 关键规则 |
|---|---|
| **加计扣除** | 其他相关费用限额 = 第一至五项之和 × 10% ÷ (1-10%)；委托研发按实际发生额 80% 计入；委托境外不超过境内符合条件研发费用的 2/3；特殊收入/试制产品材料费/政府补助冲减，不足冲减按零；负面清单行业（主营收入占比>50%）不得加计 |
| **高企认定** | 其他费用不超过研发总费用的 20%；委托外部研发按实际发生额的 80% 计入；六大指标（科技人员占比≥10%、研发费用占收入比例分档 5%/4%/3%、境内研发费用占比≥60%、高新技术产品收入占比≥60%、创新能力评价≥71分） |
| **会计准则** | 按账面实际列支金额归集，委托研发全额列支；研究阶段费用化，开发阶段满足五条件可资本化 |
| **R&D 统计** | 近似会计口径 |

测算结果可**冻结为留档快照**，供审计追溯。

### 3.2 工时 → 人工费用 自动归集

这是打通三拨人的关键一环。规则：

```
某员工在某项目的人工费用 = 员工当月薪酬 × 该项目研发工时 ÷ 该员工当月总工时
```

- 非研发工时（如培训）对应薪酬**不进入**研发费用
- 按「人 × 项目 × 月份」幂等，重复执行不会重复计账（已验证）
- 未设置薪酬的人员会被显式提示，不会静默丢弃

实测：2026-10 一个月，13 人、425 条工时明细，自动归集 **31.31 万元**人工费用到 4 个研发项目。

### 3.3 15 类备查台账

> **关于数量**：模板源码中 `LEDGERS` 数组实际包含 **15** 个台账定义
> （模板界面上的数量是动态渲染的 `LEDGERS.length`）。本平台完整实现全部 15 类，
> 未做删减。

覆盖稽查关注点，每类都带**业务规则校验**与**派生列**：

| 台账 | 自动校验示例 |
|---|---|
| 研发人员名册 | 非全时研发人员研发工时占比 <50% 判定「不得认定」；劳务派遣判定「不得认定」 |
| 研发预算与执行差异 | 差异率 >20% 且未说明原因时告警 |
| 研发资本化判定 | 五条件齐备性判定、税收年摊销（成本 200%）自动计算 |
| 委外研发台账 | 缺少科技部门登记号时提示「未登记可能不得享受优惠」 |
| 研发物料去向 | 去向为「对外销售」但未登记收入时告警 |
| 研发固定资产 | 研发生产共用资产缺少审批手续时告警 |
| 特殊收入冲减 | 自动给出对加计扣除的影响说明 |

### 3.4 备查资料 Word 生成

25 份资料，分 6 个环节，**数据自动取自系统**：

| 环节 | 份数 | 内容 |
|---|---|---|
| S1 研发组织体系 | 4 | 组织架构、研发管理制度、核算体系、科技人员激励制度 |
| S2 研发项目立项 | 4 | 立项决议、可行性报告、计划任务书、项目组清单 |
| S3 研发过程留痕 | 4 | 工时记录表、设备使用记录、阶段评审、变更记录 |
| S4 费用归集与分摊 | 6 | 辅助账、多口径汇总、工资工时分配、公共费用分配、委托研发、其他费用限额 |
| S5 申报与口径协同 | 4 | 高企指标测算、加计扣除明细表（A107012）、四口径对照、专项审计框架 |
| S6 结题成果与备查 | 3 | 结题验收、成果转化、备查清单与稽查自查 |

支持**单份下载**与**整包下载**（一个 docx 含全部 25 份）。

> **实现说明**：Word 生成不依赖任何第三方库 —— 直接构造 OOXML 并自写最小
> ZIP 写入器。原因是本系统运行在受限内网，少一个依赖就少一份供应链风险，
> 而 docx 格式本身并不复杂。已用 `unzip -t` 与 `python-docx` 双重验证
> 生成的文件可正常打开、表格与中文文本完整。

## 四、AD 用户同步：禁用与删除

系统的用户主数据来自 Active Directory，按以下规则自动同步（每小时 + 手动触发）：

| AD 中的状态 | 系统状态 | 能否登录 | 是否出现在选择列表 |
|---|---|---|---|
| 存在且启用 | `active` | ✅ 能 | ✅ 显示 |
| 存在但**已禁用** | `disabled` | ❌ 不能 | ❌ 不显示 |
| **已被删除**（或移出 `Group_AllStaffs`） | `deleted` | ❌ 不能 | ❌ 不显示 |
| 恢复启用 | `active` | ✅ 能 | ✅ 显示 |

### 为什么「删除」不做物理删除

工时、审批、费用、分摊快照都通过外键引用用户。物理删除会破坏历史数据的
可追溯性 —— 而研发费用备查资料有**留存 10 年**的合规要求。

因此采用**软删除**：记录保留、历史可查，但从以下位置彻底消失：

- 登录被拒绝
- 不在任何人员下拉/选择列表中出现
- 自动从**项目成员**中移除
- 自动从**项目审批人**中移除

### 自动级联清理

用户被禁用/删除后，系统自动执行（每次同步都会做）：

1. 从 `project_members` 移除
2. 从 `project_approvers` 移除
3. 若某项目因此没有审批人，由 **HR/管理员兜底审批**，
   并在同步结果与项目列表中提示「已无审批人」

这样不会出现「审批人是已离职人员，报工卡住无人可批」的情况。

### 同步可追溯

每次同步记录在 `ad_sync_runs` 表中，包含：
- 触发来源（启动 / 定时 / 手动）
- 新增、更新、禁用、删除、恢复的人数
- 被禁用/删除的具体用户名列表
- 级联清理的影响行数

「系统管理」页面的用户列表会显示每个用户的 **AD 状态**
（在职 / AD 已禁用 / AD 已删除），并可筛选「仅在职」或「全部」。

### 重要设计细节

**登录不会"复活"已删除的用户**。旧实现中，登录时会 upsert 用户记录，
存在把已删除用户重新激活的风险；现在 `upsertUserFromAd` 在冲突分支
**刻意不更新 `ad_status` 与 `is_active`**，这两个字段只由同步任务和管理员决定。

### 5.2 删除的安全边界

不同数据的删除策略不同，核心原则是**不破坏历史可追溯性**：

| 对象 | 删除策略 | 原因 |
|---|---|---|
| 项目 | 仅当**无任何工时/费用/审批/台账引用**时允许物理删除，否则返回 409 提示改用「停用」 | 项目被历史数据引用，删除会破坏关联 |
| 用户 | 不做物理删除，AD 同步标记 `deleted`（软删除） | 工时/费用/分摊有 10 年留存要求 |
| 考勤 | 可删除（清除误录） | 无下游依赖，能重新录入 |
| 节假日日历 | 可删除 | 无下游依赖，能重新录入 |
| 费用明细 | 可删除，但**工时自动归集的记录受保护** | 删除会破坏人工费用归集口径 |
| 台账行 | 可删除，含跨台账类型保护 | — |

### 5.3 数据一致性保障

**每日可执行完整性审计**：

```bash
sudo bash /opt/rnd-timesheet/deploy/verify-integrity.sh
```

覆盖 28 项检查：

1. **孤儿数据**（10 项）—— 所有外键引用是否有效
2. **汇总一致性**（2 项）—— 工时单合计 = 明细合计；研发+非研发 = 合计
3. **必填字段**（5 项）—— 用户名、项目号、项目名非空；工时/金额为正
4. **状态矛盾**（3 项）—— 已通过必有审批记录；已提交必有待审单；处理必有处理人
5. **AD 状态一致性**（4 项）—— `ad_status` 与 `is_active` 不矛盾；失效用户不在审批人/成员中
6. **关键约束存在性**（4 项）—— 唯一约束、幂等约束是否在位

### 5.4 已修复的一致性缺陷

审计中发现并修复：

**工时单合计与实际明细不一致**

原因：`recomputeTotals()` 在事务内调用 `repo.getEntriesForPeriod(userId, period)`
**未传入事务连接**，导致从连接池的另一条连接读到**事务提交前的旧快照**。
表现为：删除某日报填后 HTTP 返回 200，但工时单合计没有随之更新。

修复：`getEntriesForPeriod` 增加 `client` 参数，`recomputeTotals` 传入事务连接。
已验证删除 8h 填报后，工时单合计从 136 自动变为 128。

| 外部借用 | 无 AD 账号的人员（如外协、客户）可登记为外部借用方 |
| 借用历史 | 每次借还都有记录，可追溯谁在何时借走、何时归还 |
| 批量操作 | 多选批量改状态（维修/报废等）、批量删除 |
| **CSV 导出** | 按当前筛选条件导出，含 16 个字段，带 UTF-8 BOM 保证 Excel 不乱码 |

### 6.3 权限

| 角色 | 权限 |
|---|---|
| 管理员 / 人力资源部 | 全部资产的增删改、借还办理、批量操作、导出全部 |
| 其他用户（员工） | **只能查看自己名下**的资产与借用历史，可导出自己的 |

员工登录后只能看到分配给自己的设备，看不到其他人的资产信息。

### 6.4 关键设计

**使用人必须挂接 AD 账号**，不允许自由文本姓名：
- 选用人时模糊搜索 AD 账号或姓名，选中后存 `user_id` 外键
- 录入不存在的 AD 账号会被拒绝（422）
- 外部人员（无 AD）走 `borrower_external` 字段，与 AD 使用人互斥
  （数据库层有 CHECK 约束保证不会同时存在）

**状态自动推导**：
- 有 AD 使用人 → 在用
- 有外部借用方 → 外借
- 都没有 → 在库
- 维修/报废/调拨为显式指定，不会被自动覆盖

### 6.5 数据问题提示

原始 Excel 中存在**财务资产编号重复**的情况：
- `CS-02-0027` 被 3 台交换机（IT009/IT010/IT011）共用
- `CS-02-0029` 被 2 台服务器（IT005/IT006）共用

这可能是采购单号复用。系统**保留了原始数据**，但在录入时若财务编号与已有资产重复，
会给出提示（不阻断，因为共用采购单号可能是有意的）。建议由资产管理员核实后修正。

### 6.6 与原 Excel 的字段对应

导出 CSV 覆盖原始 13 个字段，并新增 3 个：

| 原始字段 | 导出字段 |
|---|---|
| 资产IT编号、财务资产编号、设备类型、品牌、型号、序列号(SN)、使用保管人、领用状态、领用日期、存放位置、供应商名称、购买日期、备注 | 全部保留 |
| — | **AD账号**（新增，指明使用人的域账号） |
| — | **外部借用方**（新增） |
| — | **最后更新时间**（新增，便于核对数据新鲜度） |

> 注：原始 Excel 的「创建人 / 修改人 / 最后更新时间」三组重复列（含 `供应商 (1)` 等
> 重名列）已合并，系统统一用 `updated_at` 记录最后变更时间。

## 七、审批路由：多主管「或签」

一个项目可以配置**多位审批人**，**任意一位批准即通过**（或签），
无需等待其他主管，避免因某人出差导致报工长期挂起。

### 配置方式

「费用归集 → 研发项目 → 编辑」中，在**项目审批人**里多选人员
（支持搜索姓名/工号/部门，可全选当前搜索结果）。一个项目可配多人，
项目列表会直接显示当前审批人；未配置的显示橙色「未配置」提示。

### 审批规则

| 情形 | 谁能审批 |
|---|---|
| 项目配置了 1 位审批人 | 该审批人 |
| 项目配置了多位审批人 | **其中任意一位**（或签，先到先得） |
| 项目未配置审批人 | 仅人力资源部 / 系统管理员（兜底） |
| 人力资源部 / 系统管理员 | 永远可审批全部单据（兜底） |

### 关键行为

- **先批先生效**：甲批准后，乙的待办中该单消失，再点会提示「该审批单已处理」
- **处理人留痕**：系统记录实际处理人（`approvals.decided_by`），可追溯是谁批的
- **收件箱隔离**：审批人只看到自己作为审批人的项目单据，看不到无关数据
- **提交时提示**：若报工涉及未配置审批人的项目，提交后提示
  「有 N 个项目未配置审批人，将由人力资源部/管理员审批」

### 升级兼容

原系统只有单一 `owner_id`。升级迁移（`004_multi_approver.sql`）会自动把
`owner_id` 转为审批人记录，**历史数据无需人工处理**；
`owner_id` 仍保留为「项目主负责人」用于展示与责任归属。

## 八、批量与多选操作

系统各模块的列表均支持**勾选、全选、批量处理**，避免逐条点击：

| 模块 | 批量能力 |
|---|---|
| **审批中心** | 多选待审单 → 批量通过 / 批量驳回（统一填写驳回原因）；支持全选本页 |
| **科技人员管理** | 多选 → 批量认定为科技人员 / 取消认定 / 批量设置研发类型 |
| **人力与考勤** | 多选人员 → 批量录入考勤；未勾选时默认处理全部在职人员 |
| **项目成员** | 搜索（姓名/工号/部门）+ 全选当前搜索结果 + 清空；显示已选人数 |
| **备查台账** | 多选行 → 批量删除（含跨台账类型保护） |
| **费用明细账** | 多选 → 批量删除；工时自动归集的记录受保护，不可误删 |

**交互细节**：
- 表头复选框支持**三态**（全选 / 未选 / 部分选中），部分选中时显示为横杠，
  避免用户误以为已全选
- 选中行**高亮显示**，批量操作条实时显示「已选 N 项」
- 危险操作（批量删除、批量驳回）均**二次确认**，并显示影响范围
- 批量操作走**后端批量接口**，而不是前端逐条循环请求
  （原批量考勤 200 人需发 200 次请求，现改为 1 次）

**安全保护**：
- 批量删除台账行时校验 `ledger_key`，防止跨台账类型误删
- 工时自动归集的费用记录不可删除，避免破坏人费归集口径
- 批量修改角色时禁止管理员把自己降级（需由其他管理员操作）
- 单次批量上限 500 条（考勤 1000 人），防止误操作造成大面积影响

## 九、相对模板的取舍

模板是单文件 HTML 工具，数据存浏览器本地、靠导出/导入协同。本平台保留了它的
**业务智慧**（口径规则、台账定义、核查要点、文档结构），重建了它的**工程形态**：

| 维度 | 模板 | 本平台 |
|---|---|---|
| 数据存储 | 浏览器 localStorage | PostgreSQL，多用户并发 |
| 协同方式 | 导出/导入 JSON 包手工传递 | 同一数据库，按角色分权，实时一致 |
| 用户体系 | 无（会员码本地校验） | AD 域账号，代码级权限控制 |
| 工时来源 | 手工在表格里填 | **对接已有工时系统**，审批后自动归集 |
| 权限 | 无 | 工程师/项目负责人/财务/人事/管理员五档 |
| 文档格式 | Markdown + .doc（伪 Word） | 标准 .docx（OOXML），可正常打开编辑 |
| 合规校验 | 客户端即时计算 | 服务端校验 + 合规自检清单 + 审计日志 |
| 依赖 | 单个 300KB HTML | 前后端分离，容器化部署 |

**未纳入的部分**（有意取舍）：

- **会员码/授权校验**——内网系统无此需求，改为 AD 域认证
- **多部门协同包导入导出**——同一数据库天然共享，无需文件传递
- **部分主观评分项**（创新能力评价得分）——无法自动计算，改为人工录入

## 十、角色与权限

系统共五档角色，权限边界经验证测试覆盖：

| 角色 | 审批 | 人事 | 财务 | 管理 | 说明 |
|---|:--:|:--:|:--:|:--:|---|
| `employee` 研发人员 | — | — | — | — | 仅填报与查看自己的数据 |
| `pm` 项目负责人 | ✓ | — | — | — | 可审批自己负责的项目 |
| `finance` 财务部 | ✓ | — | ✓ | — | 费用归集、多口径测算、备查台账与资料 |
| `hr` 人力资源部 | ✓ | ✓ | ✓ | — | 含考勤、名册、审计日志 |
| `admin` 系统管理员 | ✓ | ✓ | ✓ | ✓ | 全部权限 |

**指派方式**：管理员进入「系统管理」→ 选择用户 → 编辑 → 角色下拉选择「财务部」。
首次上线时系统中没有 `finance` 用户，需管理员手动指派。

**权限边界**（20 项测试验证）：
- 财务**可以**：查看/维护费用归集、公共费用、委外研发、15 类台账、
  多口径测算、合规自检、备查资料；查看月度工时汇总以核对人工费用口径
- 财务**不可以**：同步 AD、查看审计日志、修改用户角色、维护考勤（均返回 403）

## 十四、首次使用初始化顺序

1. **用域账号登录**（需在 `Group_AllStaffs` 组内）
2. **人事**：进入「科技人员管理」，为研发人员设置工号、岗位、学历、专业、
   聘用形式、月薪，并勾选「认定为科技人员」
3. **管理员**：在「系统管理」中指派角色 —— 财务人员设为 `finance`，
   项目负责人设为 `pm`，人力资源部设为 `hr`
4. **财务**：进入「费用归集」→「工时转人工费用」，确认预览无误后执行归集
5. **财务**：登记公共费用（折旧/水电/房租）与委外研发
6. **财务**：进入「备查台账」补录人员名册、资产、物料等台账
7. **财务**：进入「多口径测算」查看结果与合规自检，按提示整改
8. **财务**：进入「备查资料生成」，一键生成 25 份 Word

## 十五、已知限制

- **创新能力评价得分**无法自动计算，需人工录入（满分 100，≥71 达标）
- **考勤数据**目前由 HR 手工/批量录入，未对接考勤机
- **加计扣除比例**默认 100%（制造业等行业），其他行业可在企业档案中调整
- **委外研发科技部门登记号**需人工维护，系统只能提示缺失
- **多级审批**未实现（当前单级：项目负责人）
- 文档模板的**制度文本**为通用版本，企业应结合自身实际修订后使用
