# 业务系统接入统一身份（OIDC）指南

> 读者：要改造自己系统、让它支持 `sso.tri.local` 登录的开发/运维。

> **如果是要把资料发给同事**：不要只发本文——按 [给同事的交接包](接入对接包/README.md) 里的**四件套**发，
> 对方照着能独立完成接入，你只需要在 IdP 侧建 client 并做验收。

> 已接入对象：man-timesheet（工时）、knowledge-hub（知识平台）、chat-openwebui（Open WebUI）、slurm-web（集群管理）。
> 配套：[部署文档](<部署文档.md>) / [管理手册](<管理手册.md>) / [接入参考实现](../ops/integration/README.md)

## 1. 3 分钟看懂：接入后长什么样

**改造前**（现状：每个系统自己连 LDAP）

```
员工 ──输入域账号口令──► 工时系统 ──LDAP bind──► AD
                       知识平台 ──LDAP bind──► AD    ← 各系统各存一套会话、各算一次过期
                       Open WebUI ──LDAP(明文389)──► AD
```

**改造后**

```
员工 ──①点「公司账号登录」──► sso.tri.local ──LDAP bind──► AD    ②授权码回跳
         ▲                                                        │
         └──────────── ③登录后各系统免登录（浏览器带 IdP 会话） ◄──┘
```

**每个系统只做四件事**：

1. 把登录页换成「跳 IdP」；
2. 回调时用授权码换令牌（**后端**做，浏览器看不到令牌）；
3. 用令牌里的身份建立自己的会话（用户主键用 `sub`）；
4. 按**角色**授权，而不是按 AD 组名授权。

## 2. 三种接入难度（先判断你属于哪类）

| 类型 | 典型系统 | 改造方式 | 工作量 |
|---|---|---|---|
| **A. 标准 Web 应用**：只有「登录/退出」，角色就是管理员/普通用户 | knowledge-hub（知识平台） | 直接按 §5 标准流程改造 | 1~2 人日 |
| **B. 有成熟 OIDC 支持的软件**：Open WebUI、n8n、GitLab、Jellyfin 等 | chat.tri.local | 只改配置：关 LDAP、填 OIDC 参数 | 0.5 人日 |
| **C. 有自有业务角色**：权限体系复杂，AD 组参与判定 | man-timesheet（工时） | 标准流程 + **继续请求 `groups` claim** | 2~3 人日 |

判断口诀：**你的权限是不是只由"这个人是谁 + 他是不是管理员"决定？**
是 → A/B 类，直接用 IdP 角色。
否（还有"项目负责人""财务""审核人"等业务岗） → C 类，见 §7。

## 3. IdP 侧要准备什么（IT 代做，5 分钟）

每接入一个系统，在 IdP 上增加一个 **client**。目前改 `configure.py` 一处即可（配置即代码）：

```python
# deploy/scripts/configure.py 的 ensure_clients()
("my-app", "新系统名称", "https://myapp.tri.local", True),
#   ↑ clientId      ↑ 显示名        ↑ 系统根地址（决定回调白名单）  ↑ 是否启用
```

```python
# 同文件顶部的 CLIENT_SECRETS
"my-app": os.environ.get("OIDC_CLIENT_SECRET_MYAPP", ""),
```

```bash
# .env 加一行
OIDC_CLIENT_SECRET_MYAPP=$(openssl rand -hex 32)
# 应用
./deploy/deploy.sh provision
# 取 secret 交给系统负责人（只显示一次）
grep '^OIDC_CLIENT_SECRET_MYAPP=' deploy/.env | cut -d= -f2-
```

**IT 交给业务方的三样东西（缺一项对方就做不下去）**：

1. **三个连接参数**（Issuer / Client ID / Client Secret，见下表）
2. **一个文档交接包**（四个文件，见 [接入对接包](接入对接包/README.md)）
3. **一个联调联系人与验收安排**（谁在 IdP 侧看日志、什么时候一起验收）

**三个参数**：

| 参数 | 值 |
|---|---|
| Issuer | `https://sso.tri.local/realms/tri` |
| Client ID | `my-app` |
| Client Secret | `<32 字节 hex>` |

## 4. 参数速查（所有系统通用）

| 参数 | 值 / 规则 |
|---|---|
| Discovery | `https://sso.tri.local/realms/tri/.well-known/openid-configuration` |
| Authorization | `https://sso.tri.local/realms/tri/protocol/openid-connect/auth` |
| Token | `https://sso.tri.local/realms/tri/protocol/openid-connect/token` |
| UserInfo | `https://sso.tri.local/realms/tri/protocol/openid-connect/userinfo` |
| JWKS | `https://sso.tri.local/realms/tri/protocol/openid-connect/certs` |
| End Session（登出） | `https://sso.tri.local/realms/tri/protocol/openid-connect/logout` |
| Client 类型 | **Confidential**（有后端就必须保密；禁止把 secret 放前端） |
| PKCE | **必须 S256** |
| scope | `openid profile email roles`（C 类系统再加 `groups`） |
| 回调地址 | `https://<系统域名>/*`（生产建议收敛到精确路径，如 `/api/auth/oidc/callback`） |
| 签名算法 | RS256 |
| 令牌有效期 | access/ID 5 分钟；会话 8 小时 idle / 24 小时 max |

## 5. 标准接入流程（所有系统都照着做）

### 步骤 1：删除旧登录入口

- 删除用户名/密码输入框与 `POST /login` 处理；
- 删除 LDAP 连接配置（`LDAP_URLS / BIND_DN / BIND_PASSWORD`）；
- 删除 AD 定时同步任务（组信息改由令牌提供）。

> **不要**保留旧登录路径"以防万一"——保留等于永远保留。切换期用 `AUTH_MODE` 开关（见步骤 6）。

### 步骤 2：实现「发起登录」

```
GET /auth/login
  state   = 随机 24 字节
  nonce   = 随机 24 字节
  verifier= 随机 48 字节
  challenge = base64url(sha256(verifier))
  把 {state, nonce, verifier, returnTo} 存到后端（session 或一次性票据表）
  302 到 IdP：
    ?client_id=my-app
    &redirect_uri=https://myapp.tri.local/auth/callback
    &response_type=code
    &scope=openid profile email roles
    &state=<state>&nonce=<nonce>
    &code_challenge=<challenge>&code_challenge_method=S256
```

⚠️ **必须整页跳转**（`location.href`），不能 `fetch`/`ajax`：IdP 是 302 重定向，fetch 拿不到登录页。

### 步骤 3：实现「回调」

```
GET /auth/callback?code=...&state=...
  1. 校验 state 与后端保存的一致（一次性，用完即删）
  2. 后端 POST /token：grant_type=authorization_code, client_id, client_secret,
                       code, redirect_uri, code_verifier
  3. 校验 ID Token：RS256 签名（JWKS）、iss=https://sso.tri.local/realms/tri、
                    aud=my-app、exp/nbf（容差 60s）、nonce
  4. 按 sub 建立本地会话（见步骤 4）
  5. 302 回到 returnTo（只允许站内相对路径）
```

### 步骤 4：建立本地会话（关键规则）

| 规则 | 原因 |
|---|---|
| 用户主键用 **`sub`**（UUID） | 用户名会变（改名、域迁移），`sub` 不变 |
| `preferred_username` 只用于显示和**首次对账** | 迁移时按用户名把历史数据挂到 sub 上 |
| 会话 cookie：`Secure; HttpOnly; SameSite=Lax` | 防 XSS 窃取、防 CSRF；Safari 下 `SameSite=None` 反而会被拦 |
| **令牌不进浏览器** | access/refresh token 只存服务端 |
| 不要每请求去验 IdP | 本地会话 + 短角色缓存即可；IdP 短暂故障时既有会话可继续 |

首次登录对账逻辑：
```
user = 按 sub 查 → 找到就用
      → 没找到：按 preferred_username 查本地用户 → 找到则绑定 sub（记审计）
      → 都没有：创建新用户（角色 = 默认业务角色）
```

### 步骤 5：授权用角色，不用 AD 组名

```
# 反例（现状）：if user.groups.includes('Group_Roots') { allowAdmin() }
# 正例：       if roles.includes('kb:admin')      { allowAdmin() }
```

令牌里角色在 `access_token.realm_access.roles`（或 userinfo），**过滤掉 Keycloak 内建角色**
（`default-roles-tri`、`offline_access`、`uma_authorization`），只认业务角色：

`ts:admin`、`ts:finance`、`kb:admin`、`kb:reviewer`、`cluster:admin`

### 步骤 6：实现「退出」

```
POST /auth/logout
  1. 清本地会话 cookie
  2. 302 到 https://sso.tri.local/realms/tri/protocol/openid-connect/logout
       ?client_id=my-app
       &id_token_hint=<登录时的 id_token>
       &post_logout_redirect_uri=https://myapp.tri.local/
```
⚠️ 只清本地会话 = **其它系统仍是登录态**；必须走 IdP 登出，前端拿到 URL 后整页跳转。

### 步骤 7：删掉旧代码 + 回滚开关

- 切换期保留 `AUTH_MODE=oidc|ldap`，两套登录并存但默认 oidc；
- 观察 1 周验收通过后，**删除 ldap 分支**并更新本指南。

### 步骤 8（可选）：能否保留自有登录页？

可以，但**必须是独立身份域**（本地账号），**不能**在自有登录页继续校验域口令。
详见 [双登录方案](<双登录方案.md>)。一句话结论：员工系统一律纯 SSO；
"万一 IdP 挂了"的需求用**默认关闭的应急通道**解决，而不是常驻第二入口。

## 6. 各系统接入注意点

### 6.1 knowledge-hub（知识平台，A 类，推荐先做）

- 角色：`kb:admin`（管理员）、`kb:reviewer`（审核人）；普通员工无角色即可提交。
- ⚠️ 现有 `LDAP_REVIEWER_GROUPS=Group_Roots` 兜底：改造后由 `kb:reviewer` 决定，AD 建好 `Group_KBReviewers` 后重新 `provision` 即可切走。
- **必须请求 `groups` scope**（2026-11-03 已在 IdP 侧分配）：本系统的「部门」与「部门可见范围」由
  `Group_KB_<KEY>` 组推导，不请求 groups 会导致所有知识条目的部门范围失效（见 §7）。
- 角色规则**不要重写**：复用 `ldap.js` 的 `mapRole`，并取「AD 组推导」与「IdP `kb:*` 角色」的较高者，避免切换期降权。
- 删除：`LDAP_*` 全部、`LDAP_SYNC_INTERVAL_MINUTES`、登录页口令框、`POST /api/login`。
- 保留：n8n 机器接口（`N8N_WEBHOOK_SECRET`）、`OPENWEBUI_API_KEY`（机器身份与用户身份无关），以及会话/CSRF 机制。
- 完整改造包：[ops/integration/knowledge-hub/](../ops/integration/knowledge-hub/接入清单.md)

### 6.2 Open WebUI（chat.tri.local，B 类，收益最大）

- 现状 **LDAP 明文 389**，改成 OIDC 后口令不再经过它。
- 配置：`ENABLE_LDAP=false`、`ENABLE_OIDC=true`、填 issuer/client/secret/scope；
  用户组映射用 `KB_OIDC_ROLE_CLAIM` 或读 `realm_access.roles`。
- ⚠️ 切换前先在 OWUI 里手工建好管理员，删掉 `WEBUI_ADMIN_EMAIL` 自动提权机制，避免首位登录者成为管理员。
- 知识平台的 `KB_API_*` 机器接口保持不变。

### 6.3 man-timesheet（工时，C 类，见 §7 专项清单）

- 有自有业务角色（`pm/finance/hr`）→ **不能**把 `users.role` 交给 IdP 覆盖；
- 必须请求 `groups` scope，继续用 AD 组做准入与角色推导；
- 详细清单：[工时接入清单](../ops/integration/man-timesheet/接入清单.md)

### 6.4 slurm-web（集群管理，C 类敏）

- 主认证改 OIDC；`admin_users` 白名单**降级为高危操作二次确认**，不再当主认证；
- **集群 Linux 账号映射**与 SSO 无关，需单独确认 `sAMAccountName` 与集群 UID 一一对应；
- 建议最后做，先在 staging 验证。

### 6.5 Open OnDemand（集群门户，B 类，2026-11-09 已上线）

- 系统：OOD 3.1.16 于 `edas.tri.local`，Apache `mod_auth_openidc` 做 OIDC RP；
- Client：`ood`，redirect URI `https://edas.tri.local/oidc`；
- 用户名映射：`oidc_remote_user_claim: preferred_username` → `user_map_match: '.*'`，
  `preferred_username` 即 AD `sAMAccountName`，与集群 Linux 账号一致；
- 配置在 OOD 侧 `/etc/ood/config/ood_portal.yml`（含 secret，mode 600），
  部署脚本见 slurm 仓库 `scripts/setup-ood-oidc.sh`；
- 已验证：未登录 302 → Keycloak 登录 → 回调 `/oidc` → Dashboard 200；退出走 IdP；
- 额外收益：OIDC 会话替代逐请求 LDAP bind，页面加载更稳定。

## 7. C 类系统：AD 组怎么继续用

C 类系统的权限依赖「这个人属于哪些 AD 组」。做法：**请求 `groups` scope，从 userinfo 拿组名**。

```bash
# 登录时 scope 加 groups
scope=openid profile email roles groups

# 回调后后端再取一次 userinfo（带 access_token）
GET https://sso.tri.local/realms/tri/protocol/openid-connect/userinfo
→ {
    "sub": "...", "preferred_username": "linyiyao", "email": "...",
    "groups": ["Group_AgenticFlow", "Group_AllStaffs", "Group_BackupEnd", "Group_Roots"]
  }
```

规则（已在工时系统上验证）：

| 用途 | 数据来源 | 说明 |
|---|---|---|
| 准入 | `groups` ∩ `Group_AllStaffs` | 与现有 `LDAP_ALLOWED_GROUPS` 语义一致 |
| 管理员 | `groups` ∩ `Group_Roots` 或 `roles` 含 `ts:admin` | 二选一，不要两套判定同时生效 |
| 财务 | `users.role`（业务属性）+ `groups` 兜底 | 财务岗由 HR 指派，不应由 AD 单方面决定 |
| 业务角色（pm 等） | **只在本地库** | 业务负责人维护，不进 IdP |

⚠️ 组名大小写：AD 内部不区分，代码里比较时统一 `toLowerCase()`。

## 8. 安全红线（评审会逐条对照）

| # | 红线 | 反例 |
|---|---|---|
| 1 | 后端才持有 `client_secret` | 把 secret 写进前端 JS/移动端 |
| 2 | 必须校验 `state`、`nonce`、`iss`、`aud`、`exp` | 只验签名就放行 |
| 3 | 必须 PKCE S256 | 省略 `code_challenge`（Keycloak 会直接报错） |
| 4 | 回调地址精确白名单 | 用 `https://myapp.tri.local/*` 还允许开放重定向 |
| 5 | 会话 cookie `Secure; HttpOnly; SameSite=Lax` | `SameSite=None` 在 Safari 上不可靠 |
| 6 | 令牌不进浏览器、不进日志 | 打日志把 access_token 打出来 |
| 7 | 登出走 IdP 后端会话 | 只删本地 cookie |
| 8 | 不保留旧口令登录旁路 | "为稳妥"两套登录长期并存 |
| 9 | IdP 故障时不"放行" | "IdP 挂了就跳过校验" |
| 10 | 用户主键用 `sub` | 用用户名做主键 |

## 9. 自测脚本（改完先跑这个）

```bash
# 在你的系统所在机器上，用真实域账号做一次完整链路（示例：Node）
curl -sS -c /tmp/c.txt -o /dev/null -w '%{http_code} %{redirect_url}\n' https://myapp.tri.local/auth/login
# 期望：302 → https://sso.tri.local/realms/tri/protocol/openid-connect/auth?...

# 浏览器完成一次登录后，检查会话与角色
curl -sS -b /tmp/c.txt https://myapp.tri.local/api/me
# 期望：{ "user": { "sub": "...", "username": "linyiyao", "roles": ["kb:reviewer", ...] } }
```
