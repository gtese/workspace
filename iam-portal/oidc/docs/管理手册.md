## 1. 账号与权限模型

### 1.1 三类账号，职责分开

| 账号 | 用途 | 存放位置 | 谁持有 |
|---|---|---|---|
| **管理员账号**（Keycloak `admin`） | 管理控制台、`configure.py` 调用管理 API | `deploy/.env` 的 `KC_BOOTSTRAP_ADMIN_*` | IT（建议 2 人，见 §1.3） |
| **LDAP 服务账号**（`sa_ldap@tri.local`） | 只读绑定 AD、同步用户与组 | `deploy/.env` 的 `LDAP_BIND_*` | IT |
| **业务系统 client secret** | 各业务系统后端换令牌 | `deploy/.env` 的 `OIDC_CLIENT_SECRET_*` | 对应系统运维 |

> 员工自己的域账号口令**从不落库、不经手 Keycloak** —— Keycloak 只把口令转发给 AD 做绑定验证。

### 1.2 谁能登录（准入）

由 AD 组决定：同步到 Keycloak 的员工，只有**同步成功的用户**能登录（当前 100 人）。若需限制到某个组（例如只允许 `Group_AllStaffs`），见 §5.3「准入收紧」。

### 1.3 管理员账号的最佳实践

1. **不要用 `admin` 做日常操作**：为 IT 每位同事建一个自己的域账号管理员（见 §5.1）。
2. `admin` 只在"没有管理员可用"时保留，并记录口令的保管人。
3. 修改管理员口令：

```bash
# 方式一：控制台（推荐）登录 https://sso.tri.local/admin/ → 右上角 → Personal info → Signing In
# 方式二：命令行
read -s NEWPW && echo
podman run --rm --network oidc --userns=keep-id \
  -e KC_DB=postgres -e KC_DB_URL=jdbc:postgresql://db:5432/keycloak \
  -e KC_DB_USERNAME=keycloak -e KC_DB_PASSWORD="$(grep ^POSTGRES_PASSWORD deploy/.env | cut -d= -f2)" \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD="$NEWPW" \
  localhost/tri-oidc-keycloak:1.0.0 bootstrap-admin user --no-prompt --optimized \
  --username admin --password:env KC_BOOTSTRAP_ADMIN_PASSWORD
```

> ⚠️ 该命令对已存在的 `admin` 会报"已存在"；改口令请用控制台。

## 2. 日常运维

### 2.1 启停与状态

```bash
cd ~/projects/oidc-work

./deploy/deploy.sh status        # 容器状态 + 健康探针 + discovery
./deploy/deploy.sh logs kc-1     # 跟进日志（Ctrl+C 退出）
systemctl --user restart tri-oidc.service   # 重启全部容器
systemctl --user status tri-oidc.service    # 看 systemd 单元状态
podman ps --format '{{.Names}} {{.Status}}' # 看容器
```

**健康判据**：

| 检查 | 正常值 |
|---|---|
| `http://127.0.0.1:19000/health/ready` | 200 |
| `http://127.0.0.1:19001/health/ready` | 200 |
| `https://sso.tri.local/realms/tri/.well-known/openid-configuration` | 200，issuer 为 `https://sso.tri.local/realms/tri` |
| 日志含 `Finished rebalance with members [... kc-1, kc-2]` | 集群双节点 |

### 2.2 每日自动任务（已配置）

| 时间 | 内容 | 文件 |
|---|---|---|
| 02:30 | `pg_dump` 备份 | `/etc/cron.d/tri-oidc-backup` |
| 03:15 | 清理 30 天前备份 | 同上 |
| 每 5 分钟 | 健康巡检（ready + discovery + 磁盘） | `/etc/cron.d/tri-oidc-health`，日志 `~/oidc-backups/health.log` |

### 2.3 同步 AD（用户/组变更）

Keycloak 对**用户登录**是实时查 AD 的（禁用、改密码立即生效）。但**组成员变化**需要重新同步才能在令牌里体现：

```bash
./deploy/deploy.sh provision       # 会执行全量同步 + 物化用户-组关系 + 重挂角色
```

频率建议：**每周一次**，或在「有人调岗/有人加入审核组」后立即执行。
> 注意：同步是幂等的，重复执行没有副作用。

### 2.4 备份与恢复

**备份**（自动 + 手动）：

```bash
./deploy/deploy.sh backup
ls -lh ~/oidc-backups/
```

**恢复演练**（务必在测试库上练过一次，或至少在变更前做）：

```bash
# 1) 停掉 Keycloak（保留数据库）
podman stop oidc-kc-1 oidc-kc-2

# 2) 用最近备份覆盖数据库
gunzip -c ~/oidc-backups/keycloak-20261029-110724.sql.gz | \
  podman exec -i oidc-db psql -U keycloak -d keycloak

# 3) 启动并验收
podman start oidc-kc-1 oidc-kc-2
./deploy/deploy.sh verify <域账号> <域口令>
```

**备份内容**：全部 realm / 用户物化关系 / 组角色映射 / 事件（密码不备份，因为不在库里）。
**不备份但同样重要**：`deploy/.env`（client secret 与数据库口令）—— 建议放公司密码管理器或保险柜，与备份分开保存。丢了 `.env` 会导致所有 client 的 secret 对不上，需要重新轮换。

### 2.5 升级 Keycloak

```bash
# 1) 备份
./deploy/deploy.sh backup
# 2) 改进阶镜像版本
vi docker/keycloak/Containerfile     # ARG KEYCLOAK_IMAGE=docker.1panel.live/keycloak/keycloak:<新版本>
# 3) 重新构建并滚动重启
./deploy/deploy.sh build
podman stop oidc-kc-2 && ./deploy/deploy.sh up     # 先升一个实例
./deploy/deploy.sh verify <域账号> <域口令>
podman stop oidc-kc-1 && ./deploy/deploy.sh up     # 再升另一个
```

**升级前必读**：Keycloak 的升级说明（Release Notes）；重大版本（如 26→27）先在 `trivm122` 或临时目录用同一份数据卷练一次。

## 3. 接入一个新系统（最常用操作）

### 3.1 步骤一：在 Keycloak 建 client（改代码，幂等）

编辑 `deploy/scripts/configure.py` 中的 `ensure_clients()` 的 `specs` 列表：

```python
("my-new-app", "新系统名称", "https://newapp.tri.local", True),
```

并在 `CLIENT_SECRETS` 中加一行（secret 从 `.env` 取）：

```python
"my-new-app": os.environ.get("OIDC_CLIENT_SECRET_NEWAPP", ""),
```

`.env` 加：

```bash
OIDC_CLIENT_SECRET_NEWAPP=<openssl rand -hex 32>
```

应用：

```bash
./deploy/deploy.sh provision
```

### 3.2 步骤二：业务系统改造（模板）

参考 `ops/integration/` 下的三种实现骨架（Next.js / Fastify / Flask）。核心接口：

| 路由 | 行为 |
|---|---|
| `GET /auth/login` | 302 到 `https://sso.tri.local/realms/tri/protocol/openid-connect/auth`，带 `state`、`nonce`、`code_challenge(S256)`；`state/nonce/verifier` 存后端 session |
| `GET /auth/callback` | 校验 `state` → 用 code + verifier 换令牌 → 校验 `iss/aud/exp/nonce` → 以 `sub` 建会话 → 302 回原页面 |
| `POST /auth/logout` | 清本地会话 → 302 到 `end_session_endpoint`（带 `id_token_hint`、`post_logout_redirect_uri`） |
| `GET /api/me` | 返回当前用户与角色（从令牌 `realm_access.roles` 或 userinfo） |

**必须做的事**：
- 校验 `state`（防 CSRF）与 `nonce`（防重放）；
- 会话 cookie：`Secure; HttpOnly; SameSite=Lax`；
- 用户主键用 `sub`（UUID），**不要用用户名**；
- 授权用**角色**，不要读 AD 组名。

**不要做的事**：
- 不要信任 ID Token 的 `aud` 之外的客户端，每个系统用自己的 client；
- 不要在浏览器里存 access token；
- 不要保留旧的用户名口令登录旁路（一次性切换 + 回滚开关，验收后删除）。

### 3.3 步骤三：验收

```bash
# 1) 系统内的登录链路（人工或脚本）
# 2) 浏览器实测：先登录系统 A，再打开新系统，应免登录
# 3) 检查令牌里的角色：
curl -s "https://sso.tri.local/realms/tri/protocol/openid-connect/userinfo" \
  -H "Authorization: Bearer <access_token>"
```

## 4. 用户与权限

### 4.1 员工入职 / 离职 / 调岗

| 场景 | 操作 | 生效 |
|---|---|---|
| 入职 | AD 建账号并加入部门组 → `./deploy/deploy.sh provision` | 同步后即可登录 |
| 离职 | AD 禁用账号 | 登录立即被拒（Keycloak 登录时实时查 AD）；已签发令牌到期失效 |
| 调岗（改装/换部门组） | AD 改组 → 执行一次 `provision` | 下一个令牌刷新周期（≤8h）内角色更新；建议调岗后让员工重新登录 |
| 权限提升（成为审核人） | AD 加入对应组 → `provision` | 同上 |

> **注意**：Keycloak 对"用户被禁用"是登录时查 AD；**已登录会话不会立即被踢**（最长 8h idle / 24h max）。紧急情况见 §8.3。

### 4.2 调整角色映射（最常用）

`deploy/scripts/configure.py` 顶部：

```python
ROLE_MAPPINGS = {
    "kb:admin":      ["Group_Roots"],
    "kb:reviewer":   ["Group_KBReviewers", "Group_Roots"],
    "ts:admin":      ["Group_Roots"],
    "ts:finance":    ["Group_Finance", "Group_Roots"],
    "cluster:admin": ["Group_Roots"],
}
```

- **加一个系统角色**：先在 `ensure_roles()` 里加角色，再在 `ROLE_MAPPINGS` 里配 AD 组。
- **改了 AD 组名**：改这里 + 执行 `provision`（组同步会带上新组名）。
- ⚠️ 若 AD 里还没有某个组（如 `Group_KBReviewers`），配置里写了也不会报错，只会打印 `! AD 组 XXX 未同步`，此时以兜底组为准。

### 4.3 会话时长调整

`configure.py` 的 `ensure_realm()` 里有会话参数（新装时生效）。**已部署的实例要改**，用控制台：

`Realm settings → Sessions`：
| 参数 | 当前值 | 调整建议 |
|---|---|---|
| SSO Session Idle | 8h | 与业务系统会话一致，不建议超过 8h |
| SSO Session Max | 24h | 每天至少重新认证一次 |
| Access Token Lifespan | 5m | 不变 |
| Client Session Idle/Max | 8h / 24h | 不变 |

⚠️ **不做 MFA 就不要把 Idle 调到 1 天以上**：口令一旦泄露，攻击者的可用窗口等于会话时长。日后若开启 MFA（§7），可适度放宽。

### 4.4 登录安全策略（爆破防护）

`Realm settings → Security defenses`（当前已开）：

| 参数 | 当前 | 说明 |
|---|---|---|
| 失败阈值 Failure factor | 5 次 | 达阈值后临时锁定 |
| 递增等待 Wait increment | 60 s | 每次失败后等待递增 |
| 最长等待 Max wait | 900 s | 15 分钟封顶 |
| 锁定时长 Max delta | 12 h | 超时后计数清零 |

> 域控侧的 `lockoutThreshold` 当前为 0（不锁定），因此**Keycloak 是防爆破的第一道闸**。如果以后 AD 开启锁定策略（如 5 次锁 30 分钟），请把这里的阈值设为 **3 次**，让 Keycloak 比 AD 更早拦截，避免员工被锁在域上影响登录电脑。

## 5. 管理控制台常用操作

登录：`https://sso.tri.local/admin/`（仅内网网段可访问，见 nginx 白名单）→ realm 选择 `tri`。

### 5.1 给 IT 同事建管理员账号

1. 确认他的域账号已同步（`Users` 里搜到）。
2. `Users → <账号> → Role mapping → Assign role → Filter by realm roles → admin`。
3. 该账号即可通过 `/admin/` 登录管理（口令走 AD，不需要另设）。

> 建议至少 2 个管理员，且都使用**域账号 + admin 角色**，不用共享 `admin`。

### 5.2 临时禁用/启用某个系统的登录

- 单个 client：`Clients → <client> → Client enabled` 开关关闭 → 该系统的登录直接失败，其它系统不受影响。
- 全员停用（维护窗口）：`Realm settings → General → Enabled` 关闭。**注意**：所有系统都会掉线，且管理员也无法登录控制台（需用 `--spi-login-...` 或重新打开）。

### 5.3 准入收紧（只允许某些 AD 组登录）

两种做法：
- **推荐**：AD 侧把非准入人员的账号移到禁用/不参与 AD 同步的范围；或
- Keycloak 侧：`User federation → AD → 用户搜索条件` 加过滤器（能被 Keycloak 正确分页查询的形式，例如 `(memberOf=CN=Group_AllStaffs,DC=tri,DC=local)`），保存并同步一次。**改完必须验收**：确认准入组内至少 2 人能登录、组外 1 人被拒。

### 5.4 查看"谁在什么时候登录了哪里"

`Sessions` 页：按用户查当前会话（含 IP、客户端、上次活动）。
历史审计：`Events`（登录事件）/ `Admin events`（配置变更），保留 180 天。也可直接查库：

```bash
podman exec oidc-db psql -U keycloak -d keycloak -c \
 "select event_time, type, username, client_id, ip_address, error
    from event_entity order by event_time desc limit 20;"
```
> `event_time` 为毫秒时间戳。

### 5.5 单点登出 / 踢掉某人的所有会话

`Sessions → <用户> → Sign out all active sessions`。
紧急场景（离职）：先在 AD 禁用，再在 Keycloak 踢会话（见 §8.3）。

## 6. 故障速查表

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| 打不开 `https://sso.tri.local` | nginx 挂 / DNS / 证书 | `systemctl status nginx`；`curl -v https://sso.tri.local/realms/master` |
| 502 Bad Gateway | SELinux 阻止 nginx 出站，或容器未就绪 | `getsebool httpd_can_network_connect` 应为 on；`./deploy/deploy.sh status` |
| 登录页能开，输入口令报"账号或口令错误" | AD 绑定/同步问题 | `podman logs oidc-kc-1 \| grep -i "ldap\|sync"`；检查 `sa_ldap` 口令是否过期 |
| 登录成功但系统里没有角色 | 用户-组关系未物化 | `./deploy/deploy.sh provision` 后重新登录 |
| 所有系统都跳登录页、且登不上 | 管理员/数据库故障 | `./deploy/deploy.sh status`；严重时按 §2.4 恢复备份 |
| 容器反复重启（Restarting） | 数据库不可达 / 镜像构建问题 | `podman logs oidc-kc-1`；对照 [排障笔记](<排障笔记.md>) §1、§2 |
| 员工 Mac 提示证书不受信 | 根证书没装 / fullchain 缺失 | 见 [部署文档 §3.1](<部署文档.md>) 与 [Mac 方案] |
| 登出后其他系统还是登录态 | 业务系统未接入 IdP 登出 | 属于接入问题，不是 IdP 故障；按 §3.2 补齐 `/auth/logout` |

更细的排错步骤见 [排障笔记](<排障笔记.md>)。

## 7. 安全加固路线（按优先级）

| 优先级 | 项 | 说明 |
|---|---|---|
| P0 | **签发 `sso.tri.local` 专用证书**（4096 位，独立私钥） | 现在用的是 `*.tri.local` 通配证书，私钥已复制到多台机器。`./deploy/scripts/issue-sso-cert.sh csr` 生成 CSR 交 CA 签发；换证后改 nginx 即可 |
| P1 | **管理员启用 MFA（TOTP）** | `Authentication → Required actions → 给管理员加 OTP`，或对 `admin` 角色配置 Conditional OTP |
| P1 | **收紧管理控制台访问** | nginx 当前允许内网网段，可进一步改为仅跳板机 IP |
| P1 | **轮换 `sa_ldap`** | 现有服务账号被 3 个系统共用。建议新建只读 `sa_oidc`，仅授权读 `DC=tri,DC=local` 的人员属性与 `Group_*` |
| P2 | 缩短会话 + MFA 全员 | 会话缩短到 4h、启用可选 OTP |
| P2 | 接入 SIEM/日志平台 | 订阅 `events` 表或 Keycloak 日志 |
| P3 | 启用 `slurm-web` 等新系统 | 见 §3 |

## 8. 变更与应急

### 8.1 变更流程（建议）

1. 在 Git 仓库分支上改（`configure.py` / `compose.yaml` / nginx 配置）；
2. 合并前跑 `make lint`（realm JSON、Python、shell、compose、密钥扫描）；
3. 生产：`git pull` → `./deploy/deploy.sh provision`（或 build+up）；
4. `./deploy/deploy.sh verify <账号> <口令>` 通过；
5. 在 [排障笔记](<排障笔记.md>) 的变更记录里写一行。

**所有配置改动以仓库为准**：不要在控制台里手工改完不落到仓库，否则下次 `provision` 会被覆盖。

### 8.2 回滚

| 场景 | 回滚方式 |
|---|---|
| 只是配置改坏了 | `git revert` → `./deploy/deploy.sh provision` |
| 升级 Keycloak 出问题 | `docker/keycloak/Containerfile` 改回旧版本 → `deploy.sh build` → 滚动重启；数据卷不动 |
| 数据库问题 | §2.4 恢复备份 |
| 彻底停用 | `systemctl --user stop tri-oidc`；各业务系统切回自己的 LDAP 登录 |

### 8.3 应急：怀疑账号被盗 / 员工离职当天

```bash
# 1) AD 禁用账号（IT 域控侧）
# 2) 踢掉 Keycloak 会话
TOKEN=... # 控制台管理员 token；或在控制台 Sessions 页面点 Sign out all
curl -s -X DELETE "https://sso.tri.local/admin/realms/tri/users/<user-id>/sessions" \
  -H "Authorization: Bearer $TOKEN"
# 3) 查该账号最近登录
podman exec oidc-db psql -U keycloak -d keycloak -c \
 "select event_time, type, client_id, ip_address, error from event_entity \
   where username='<账号>' order by event_time desc limit 50;"
```

### 8.4 应急：IdP 挂了，业务系统还能不能用

- 已登录用户的会话在业务系统侧是本地 cookie，**IdP 短暂不可用时既有会话仍可继续**（前提是业务系统不在每个请求里去验 IdP）。
- 需要登录的用户无法登录 → 这是**预期行为**（不要设计"IdP 挂了就放行"的后门）。
- 双实例互为备份：单实例故障时 nginx 自动切到另一台，无需人工干预。
