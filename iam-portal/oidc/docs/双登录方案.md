# 业务系统「双登录」方案：SSO 与自有登录页并存

> 问题：能不能让业务系统**既支持 sso.tri.local 登录，又保留自己的登录页**？
> 结论先给：**技术上可以，但默认不要做。**如果确有需要（如外包/临时账号、紧急兜底），
> 本文给出安全地做的完整设计。配套：[业务系统接入指南](<业务系统接入指南.md>) / [工时接入清单](../ops/integration/man-timesheet/接入清单.md)

---

## 1. 先分清三种「双登录」，它们的风险完全不同

| 方案 | 形态 | 员工会不会看到两个入口 | 是否保留域口令输入 | 评价 |
|---|---|---|---|---|
| **A. 双入口，同一身份** | SSO 按钮 + 「本地账号登录」 | 会 | 是（给本地账号用，不是域口令） | ✅ 有条件接受（唯一推荐） |
| **B. 双入口，同一域账号** | SSO 按钮 + 自有的域账号口令页 | 会 | **是** | ❌ 不建议（等于没改造） |
| **C. 自动回退** | SSO 失败时自动跳到本地登录页 | 不会 | 是 | ❌ 最危险（绕过监控的常态路径） |

**方案 B 为什么不可接受**：业务系统保留「域账号 + 口令」的登录页，意味着
1. 员工/攻击者会看到两个都能用的入口，**绝大多数人会用更熟悉那个**（自有登录页）；
2. 口令仍然落在业务系统进程里（日志、崩溃转储、内存），**这套 SSO 就等于没上**；
3. AD 的失败计数/锁定会在两个地方叠加：Keycloak 里的 5 次失败节流保护不了业务系统的口令框，**AD 本轮投入的最大安全收益（口令集中）归零**；
4. 审计出现两个真相源，"谁在什么时候登录了哪里"又得拼日志。

**方案 C 为什么最危险**：把失败回退做成"自动"后，攻击路径变成「先让 SSO 报错，再走本地口令」，
而运维看到的现象是"SSO 偶发失败"，长期形成"本地登录是常态"的错觉。

---

## 2. 「双登录」真正合理的三种场景

| 场景 | 为什么需要 | 正确做法 |
|---|---|---|
| **外包 / 临时人员没有域账号** | 不能给他们发 AD 账号（合规、人数、离职回收） | IdP 建立专用 client + 仅对该 client 开放「本地用户」登录策略（§3.4），或更简单：给外包建 AD 账号但只放准入组 |
| **IDP 故障时的紧急通道** | 全公司登录依赖 IdP | 应急账号 + 本地登录，**默认关闭，故障时由运维打开**（§3.3），并必须有审计告警 |
| **迁移期（1~2 周）** | 出错要回滚 | 迁移期内本地登录保留，但**只对管理员开放**（§3.5），普通员工强制走 SSO |

**不存在**和 SSO 并列给全员开的「域账号本地登录」场景——这就是 B 方案，不应该做。

---

## 3. 推荐设计：方案 A（双入口）＋ 本地账号体系独立

### 3.1 核心原则

```
           ┌───────────────► sso.tri.local ──► AD              （员工，99% 的人）
           │                （域账号，口令只在 IdP）
员工 ──────┤
           └───────────────► 本系统登录页 ──► 本地账号表       （外包/临时/应急，极少数）
                                  （口令哈希在业务库，绝不转发 AD）
```

1. **两条通道必须绑定不同的身份域**：
   - SSO 通道 → AD 身份（`sub` 是 Keycloak UUID）；
   - 本地通道 → 本地账号（`username` + 本地哈希），**绝不能**拿它去 AD 做 bind。
2. **本地账号不参与业务主数据**：不能出现在工时审批人、财务角色、知识审核人里，或必须显式白名单。
3. **两条通道各有独立审计**，且在同一张表里可区分 `auth_source = 'oidc' | 'local'`。
4. **本地账号口令策略独立**：≥12 位随机、90 天轮换、不可与域口令相同（技术上无法完全校验，用制度约束）。
5. **本地登录页默认低可见度**：SSO 是主按钮，本地入口排在下方（或藏到 `/login?local=1`），避免员工误用。

### 3.2 工时系统（man-timesheet）落地形态

现有代码已具备大部分骨架：

| 层 | 改动 |
|---|---|
| 数据库 | `users` 表加 `auth_source`（已有迁移）、`local_password_hash`（bcrypt）、`local_login_enabled`（bool） |
| 后端 | 保留现有 `POST /api/auth/login`，但**查询条件改为 `local_login_enabled = true AND local_password_hash 非空`**，且**不再调用 `authenticateUser`（LDAP bind）** |
| 准入 | 本地账号不走 `LDAP_ALLOWED_GROUPS` 判定（它们不在 AD 里），改为"是否为本地账号 + 是否启用" |
| 角色 | 本地账号的角色只能是 `employee`（或显式指派），**不能是 admin/finance/hr**（除非由 IT 特批并记录） |
| 前端 | `LoginView.vue`：主按钮「使用公司账号登录」+ 下方次要链接「本地账号登录」（跳 `?mode=local`） |
| 审计 | `repo.audit(..., { via: 'local' })`，并在 `/api/admin/audit` 里可按来源过滤 |

> ⚠️ 如果本地账号也要能进财务页，那就不叫"临时通道"，是完整的第二套账号体系——请先想清楚治理归属（谁批、谁审、离职怎么回收），再来加功能。

### 3.3 应急通道（推荐做法：默认关闭）

```bash
# 业务系统 .env
LOCAL_LOGIN_MODE=emergency     # off | emergency | allow
# off       → 只有 SSO（默认，上线后就是这个）
# emergency → 仅在 LOCAL_LOGIN_UNTIL 之前有效，且只允许 LOCAL_LOGIN_USERS 里的人
# allow     → 常驻本地登录（仅外包场景使用，需安全评审）
LOCAL_LOGIN_USERS=ops-01,ops-02     # 逗号分隔的本地运维账号（不带域身份）
LOCAL_LOGIN_UNTIL=2026-11-05T00:00:00+08:00
```

后端启动时校验：
- `emergency` 模式下，超过 `LOCAL_LOGIN_UNTIL` 自动关闭本地登录并告警；
- 每次本地登录发**告警**（邮件/群 webhook），而不是只写日志——应急通道被使用时，你希望当天就知道。

**为什么不用"自动回退"**：自动化的应急通道 = 常态化的第二入口。必须是人来开门、有人记录。

### 3.4 外包账号的正确做法（优先于自建本地账号）

| 做法 | 评价 |
|---|---|
| **给外包建 AD 账号，只放准入组** | ✅ 最佳：回收与员工生命周期一套流程，SSO 照常生效 |
| IdP 里建「外部用户」realm/组，本系统对其单独开放 | ✅ 好：需要 IdP 侧支持多 realm 或外部身份联邦 |
| 业务系统自建本地账号 | ⚠️ 最后手段：增加一套账号表与回收责任，且容易失控（§3.2 的约束必须坚持） |

### 3.5 迁移期回滚（工时系统清单已包含）

```bash
# 迁移期：本地（域账号）登录只对管理员开放，用于出问题时自查
AUTH_MODE=oidc
LDAP_FALLBACK_ADMIN_ONLY=true
```

迁移期结束后**删除** `POST /api/auth/login` 的域口令分支与前端口令框（工时清单第 8 步）。

## 4. 反面清单：不要这样做

| 做法 | 为什么不行 |
|---|---|
| SSO 与自有域口令页长期并列、对全员开放 | 等于没上 SSO；口令仍进业务系统 |
| SSO 失败**自动**跳本地登录 | 攻击者可刻意制造失败，本地登录成为常态路径 |
| 本地登录页复用 `LDAP bind` 校验域口令 | 保留了 100% 的口令暴露面，且与 IdP 双写失败计数 |
| 本地账号能拿 admin/finance 角色 | 绕过了 IdP 的组→角色治理，权限审计失真 |
| 本地登录不记 `auth_source` | 事后无法区分"这个人是从哪进来的" |
| 两套会话互不登出 | 从一个通道登出，另一个通道仍在线；必须统一在 `logout` 时清空全部 |

---

## 5. 决策建议（给你的直接结论）

1. **员工系统一律纯 SSO**（工时、知识平台、Open WebUI、slurm-web）。"能不能也保留登录页"这个问题，大部分时候真正想解决的是**"万一 SAML/OIDC 挂了怎么办"**——这应该用**应急通道（默认关闭）**解决，而不是常驻第二入口。
2. **确实需要本地账号的**（外包、临时）：优先走 AD 账号 + 准入组；确实不行，再按 §3.2 做，并满足 §3.2 的全部约束。
3. **要做"双入口"的**，按方案 A 做，并同步更新两处：
   - 本系统的登录页文案与安全说明（明确"本地账号仅限授权人员"）；
   - IdP 侧的 client 说明（记录该 client 存在非 IdP 身份）。
4. **上线后的验收**新增 3 条（§6）。

## 6. 双登录模式的验收清单（在标准清单基础上新增）

| # | 用例 | 期望 |
|---|---|---|
| 1 | 普通员工访问业务系统 | **只能**通过 SSO 进入；本地登录页明确提示"请联系 IT 开通本地账号" |
| 2 | 用域账号 + 口令尝试本地登录页 | **失败**（本地登录只认本地账号，不做 AD bind） |
| 3 | 本地账号登录 | 成功，但审计里 `via=local`；该账号**不能**访问财务/管理页面 |
| 4 | 本地账号离职/停用 | `local_login_enabled=false` 后立即不可登录；不依赖 AD |
| 5 | `LOCAL_LOGIN_MODE=emergency` 且过期 | 本地登录自动关闭，并有告警 |
| 6 | 任意通道登出 | 本地会话与 IdP 会话同时清理 |

---

## 7. 一句话回答

**可以并存，但要"两套身份、两种风险、一个人来开门"**：
SSO 是员工唯一的主通道；自有登录页只服务「不在 AD 里的人」，或者作为「默认关闭的应急门」。
如果"保留登录页"指的是让员工继续用域账号在那里输口令——那不建议做，也不值得做。
