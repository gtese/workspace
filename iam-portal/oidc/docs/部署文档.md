## 1. 这套系统是什么

企业内网的**统一登录（SSO）中心**。员工用一个域账号，一次登录，即可访问所有接入了 SSO 的内部系统。

```
             员工 MacBook（Safari / Chrome，无需安装任何客户端）
                          │  https://sso.tri.local  （唯一的登录页）
                          ▼
   ┌─────────────────────────────────────────────┐
   │  nginx（宿主，443，TLS 终止）                │
   └──────────────┬──────────────────────────────┘
                  │ HTTP
      ┌───────────┴───────────┐
      ▼                       ▼
  Keycloak kc-1           Keycloak kc-2        （双实例，一个挂了另一个顶上）
      └───────────┬───────────┘
                  │ JDBC（共享库）+ Infinispan 集群（会话共享）
                  ▼
            PostgreSQL 16  oidc-pgdata
                  │
                  │ LDAPS 636 + 企业根 CA 校验
                  ▼
        AD 域控 tri-sh-dc01 / dc02（认证与组成员的事实来源）
```

**它解决什么**：现状是每个系统各自用 LDAP 直连 AD 登录，员工要输 4 次域口令、撤权限要等各系统 60 分钟同步、Open WebUI 甚至走明文 389。接入统一身份后：

| 项 | 改造前 | 改造后 |
|---|---|---|
| 登录次数 | 每个系统各 1 次 | 浏览器生命周期内 1 次（SSO） |
| 口令暴露面 | 每个系统都接收域口令 | 只有 Keycloak 接触口令，业务系统只收令牌 |
| 权限调整生效 | 各系统 60 min 同步 + 会话 480 min | 组映射配置生效后，下个刷新周期（≤8h）内 |
| 登出 | 只清本站 cookie | 一次登出，全站失效 |
| 审计 | 散落在各系统 | Keycloak 统一记录登录/令牌/管理操作 |
| 新系统接入 | 重写一套 LDAP 登录 | 加一个 client + 5 个环境变量 |

### 1.2 角色模型

AD 组是**事实来源**，Keycloak 负责把组翻译成业务角色。业务系统只读角色，**不读 AD 组名**。

| 业务角色 | 授予的 AD 组 | 说明 |
|---|---|---|
| `kb:admin` | `Group_Roots` | 知识平台管理员 |
| `kb:reviewer` | `Group_KBReviewers`、`Group_Roots`（兜底） | 知识审核人。⚠️ AD 尚无 `Group_KBReviewers`，当前只有 Group_Roots 能审 |
| `ts:admin` | `Group_Roots` | 工时系统管理员 |
| `ts:finance` | `Group_Finance`（尚未建组）、`Group_Roots` | 工时系统财务 |
| `cluster:admin` | `Group_Roots` | 集群管理后台 |

映射规则**只维护在一处**：`deploy/scripts/configure.py` 顶部的 `ROLE_MAPPINGS`。改完执行 `./deploy/deploy.sh provision` 即生效，不需要重启任何服务。

## 3. 快速开始（从零到可用，共 6 步）

> 适用于新机器或重建环境。已部署的机器日常操作见 [管理手册](<管理手册.md>)。

### 3.1 前置条件

| 依赖 | 说明 |
|---|---|
| rootless podman + podman-compose | `podman 4.9`、`podman-compose 1.0.6`（EPEL 有包：`dnf install podman-compose`） |
| 用户 subuid/subgid | `usermod --add-subuids 100000-165535 --add-subgids 100000-165535 linyiyao` |
| `user.max_user_namespaces` | ≥ 15000（写在 `/etc/sysctl.d/99-oidc-podman.conf`） |
| nginx | `dnf install nginx` |
| SELinux | nginx 需要 `httpd_can_network_connect`（deploy.sh 自动设置） |
| 证书 | `deploy/certs/` 下放 `tri.local_ca.crt`（根）、`tri.local.crt`（**fullchain**）、`tri.local.key` |
| 外网 / 镜像源 | 官方 `quay.io/keycloak` 在内网不可达；使用 Docker Hub 镜像 `docker.1panel.live/keycloak/keycloak:26.8.1`（见 §7.2） |

### 3.2 部署步骤

```bash
git clone https://git.tri.local/it/oidc.git ~/projects/oidc-work
cd ~/projects/oidc-work

# ① 准备密钥（不要把 .env 提交到 Git）
cp deploy/.env.example deploy/.env
vi deploy/.env            # 填 POSTGRES_PASSWORD / KC_BOOTSTRAP_ADMIN_PASSWORD /
                          # LDAP_BIND_PASSWORD / 4 个 client secret（都可 openssl rand 生成）
chmod 600 deploy/.env

# ② 放证书
cp /path/to/tri.local_ca.crt /path/to/tri.local.crt /path/to/tri.local.key deploy/certs/
chmod 600 deploy/certs/tri.local.key

# ③ 一键部署（构建镜像 → 起容器 → 装 nginx → 配置 realm → 验收）
./deploy/deploy.sh all <域账号> <域口令>

# ④ 注册开机自启（systemd 用户单元 + linger）
loginctl enable-linger linyiyao        # 已由管理员执行，无需重复
./deploy/deploy.sh systemd

# ⑤ 系统级配套（需 sudo，一次性）
sudo ./ops/install-host.sh             # SELinux/证书/nginx/备份 cron/巡检 cron
```

`deploy.sh all` 分六步，每步都可单独执行：

| 命令 | 作用 |
|---|---|
| `./deploy/deploy.sh build` | 构建 Keycloak 运行时镜像（企业根 CA + 预构建） |
| `./deploy/deploy.sh up` | 启动/更新 PostgreSQL + 两个 Keycloak 实例 |
| `./deploy/deploy.sh nginx` | 安装 `sso.tri.local` 反代站点并重载 nginx |
| `./deploy/deploy.sh provision` | 配置 realm：AD 联邦、组→角色、client、审计（**幂等**） |
| `./deploy/deploy.sh verify <账号> <口令>` | OIDC 端到端验收（14 项） |
| `./deploy/deploy.sh systemd` | 注册 `tri-oidc.service` 开机自启 |

### 3.3 部署完成判据

```bash
./deploy/deploy.sh status
# 期望：
#   kc-1 ready 200 / kc-2 ready 200 / discovery 200
./deploy/deploy.sh verify linyiyao '***'
# 期望：结果 14/14 通过
./deploy/scripts/configure.py verify     # 需要 .env 已加载，见管理手册
# 期望：校验结果：通过 ✓
```

## 5. `configure.py` 做了什么（幂等）

| 步骤 | 内容 | 可重复执行 |
|---|---|---|
| `ensure_realm` | 创建 `tri` realm（不存在时） | ✓ |
| `ensure_ldap` | LDAP 用户联邦（**AD，READ_ONLY**）：LDAPS 636、`sa_ldap` 绑定、**parentId 必须是 realm 内部 UUID** | ✓ |
| `ensure_group_mapper` | AD 组 → Keycloak 组（`group-ldap-mapper`，关闭嵌套继承，见排障笔记 §3） | ✓ |
| `ensure_roles` | 5 个业务角色 | ✓ |
| `ensure_group_claims_scope` | `roles` client scope，并加入 realm 默认 scope | ✓ |
| `ensure_clients` | 4 个业务 client（confidential，精确回调，PKCE S256） | ✓ |
| `ensure_verify_client` | 验收用公开 client `oidc-verify` | ✓ |
| `sync_users` | 全量同步 AD 用户与组（100 用户 / 59 组，约 10 s） | ✓ |
| `sync_user_groups` | 把每个用户的 AD 组**物化**为用户-组关系（56/100 用户有组） | ✓ |
| `map_roles` | 按 `ROLE_MAPPINGS` 把 AD 组映射为业务角色 | ✓ |
| `ensure_events` | 开启登录/管理审计事件（保留 180 天） | ✓ |

```bash

./deploy/deploy.sh provision
```

## 7. 本次部署的关键决策与原因

### 7.1 Keycloak 版本：官方 Docker Hub 镜像 26.8.1

- **原因**：本机访问 `quay.io` 可行但极慢/不稳定，而官方仓库 `docker.1panel.live/keycloak/keycloak` 可秒级拉取且为**官方镜像**（与 quay 同源），版本 26.8.1（2026-10 发布）。
- 镜像名固定为 `localhost/tri-oidc-keycloak:1.0.0`，升级时改 `Containerfile` 的 `KEYCLOAK_IMAGE` 并重新 `deploy.sh build`。

### 7.2 自建镜像的两个必要改动（`docker/keycloak/Containerfile`）

1. **内置企业根 CA**（`keytool -importcert` 写进 `cacerts`）。官方镜像没有 `tri.local` 根 CA，Keycloak 连 LDAPS 会报 `PKIX path building failed`。不用 `update-ca-trust`（镜像缺 p11-kit，会报 `libp11-kit.so.0 not found`）。
2. **构建期 `kc.sh build`**。生产模式 `start --optimized` 要求镜像里已有构建产物，否则容器每 3 秒重启一次并提示 `The '--optimized' flag was used for first ever server start`。

### 7.3 双实例 + JDBC 共享库 + TCPPING 集群

- 数据库共享 → 用户/会话/配置一致；Infinispan 集群 → 会话在实例间复制，单实例重启不掉线。
- 集群发现用 **TCPPING 静态成员表**（`kc-1[7800],kc-2[7800]`），不依赖组播（内网禁组播）也不依赖 DNS 发现。
- nginx upstream：`kc-1` 主、`kc-2` backup，主实例故障自动切换。

### 7.4 组 → 角色映射（本方案最重要的设计）

```
AD 组（HR/IT 维护） → Keycloak 组（group-ldap-mapper 同步） → 组上挂 realm 角色（configure.py 的 ROLE_MAPPINGS） → 用户令牌 realm_access.roles
```

- **为什么不用 role-ldap-mapper 直接把 AD 组变角色**：它会把 AD 全部内建组（Domain Admins、Backup Operators…）都灌进 realm，共 62 个，治理不可控（见排障笔记 §4）。
- **为什么要「物化」用户-组关系**：Keycloak 的 group-ldap-mapper 下用户组是查询时动态解析的，用户-组关系表为空时令牌里**不会**出现组角色；`configure.py sync_user_groups` 把它写回（详见排障笔记 §5）。

### 7.5 会话时长：与现状对齐

| 参数 | 值 | 含义 |
|---|---|---|
| SSO Session Idle | 8 小时 | 与现有业务系统 480 min 会话一致，午休回来不用重登 |
| SSO Session Max | 24 小时 | 每天至少重新认证一次 |
| Access / ID Token | 5 分钟 | 浏览器从不持有，仅后端交换 |
| Refresh Token | 随会话 | 业务后端静默续期 |
| 登录失败锁定 | 5 次 / 12 小时窗口 | 防爆破（同时避免误锁影响早高峰，见管理手册 §4） |

## 9. 业务系统接入（后续工作，按本文档即可执行）

统一接入模式（详细参考实现见 `ops/integration/` 与《管理手册》第 6 章）：

1. **删登录页**：不再有用户名/密码输入框，改为「使用公司账号登录」按钮。
2. **跳 IdP**：`GET https://sso.tri.local/realms/tri/protocol/openid-connect/auth?client_id=<id>&redirect_uri=<https://xxx.tri.local/*>&response_type=code&scope=openid profile email roles&state=..&nonce=..&code_challenge=..&code_challenge_method=S256`
3. **回调**：`/auth/callback` 用 `client_id + client_secret + code + code_verifier` 换令牌，校验 `iss/aud/exp/nonce`。
4. **建本地会话**：cookie 用 `Secure; HttpOnly; SameSite=Lax`，以 `sub` 作为主键（不要用用户名）。
5. **授权**：读令牌里的 `realm_access.roles`（或 userinfo），按业务角色判断。
6. **登出**：本地清会话 → 跳 IdP `end_session_endpoint`（带 `id_token_hint`、`post_logout_redirect_uri`）。
7. **删除**：所有 `LDAP_*` 环境变量、AD 同步任务、组名常量。

**接入顺序建议**：先 `chat-openwebui`（现状明文 LDAP，收益最大）→ `knowledge-hub` → `man-timesheet` → `slurm-web`。每个系统切换后观察 1 周再切下一个；每个系统保留 `AUTH_MODE=oidc|ldap` 回滚开关，全部验收后删除旧分支。

**验收标准**：同一浏览器首次登录后其余系统免登录；AD 改组后 ≤1 个刷新周期生效；代码中 `grep -r LDAP_` 只剩 IdP 仓库自身。
