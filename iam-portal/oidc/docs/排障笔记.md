> 所有非预期问题、根因与最终解决办法。**下次重建/升级时先看这份，能少走大半天弯路。**

## 0. 环境事实（先记住这几条）

| 事实 | 影响 |
|---|---|
| 主机 Rocky Linux 8.10，SELinux **Enforcing** | nginx 不能主动连接其他端口；证书放进非标准目录会受限 |
| 只有 `linyiyao` 普通用户 + `sudo`；`podman` 是 **rootless** | 容器端口、数据卷权限、systemd 单元都要按用户级考虑 |
| 默认 **没有 subuid/subgid** | rootless podman 只能单映射，镜像解包 `lchown` 失败 |
| 外网：`quay.io` 慢/不稳，`github.com` 不通，`docker.io` 官方端点不通；**Docker Hub 镜像站可用** | 用 `docker.1panel.live/keycloak/keycloak:<版本>`（官方镜像的 Hub 副本） |
| 内网 DNS 正常，`sso.tri.local → 172.16.50.101` 已存在 | 不用改 hosts |
| AD 域控 `tri-sh-dc01/dc02.tri.local`，LDAPS 636 可用，证书由企业根 CA 签发 | Keycloak 必须内置企业根 CA |
| **AD 对无分页的子树搜索会超时/reset**（返回 4 个 entry 后断开） | 不要自己写脚本直连 AD 做大范围搜索；用 Keycloak 的分页 |
| AD 对 LDAP 过滤器的 BER 编码要求严格 | 手写过滤器极易报 `DSID-0C0C0Axx: unable to decode` |

## 1. rootless podman 解包镜像失败

**现象**
```
Error: copying system image from manifest list: ... processing tar file(potentially
insufficient UIDs or GIDs available in user namespace (requested 0:12 for /var/spool/mail):
Check /etc/subuid and /etc/subgid ... lchown /var/spool/mail: invalid argument
```

**原因**：用户没有 subuid/subgid 段。

**解决**：
```bash
sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 linyiyao
grep linyiyao /etc/subuid /etc/subgid
```

## 2. Keycloak 镜像里没有企业根 CA → LDAPS 失败

**现象**
```
javax.naming.CommunicationException: tri-sh-dc01.tri.local:636
  [Root exception is javax.net.ssl.SSLHandshakeException: PKIX path building failed:
   sun.security.provider.certpath.SunCertPathBuilderException:
   unable to find valid certification path to requested target]
```
同时 `testLDAPConnection` 返回 `{"errorMessage":"SSLHandshakeFailed"}`。

**排查过程（走过的弯路）**：
1. 先试 `KC_TRUSTSTORE_PATHS` + 挂载 `cacerts`：容器启动时报
   `Failed to initialize truststore ... (Permission denied)`——Keycloak 启动时会**写**信任库（转换格式）。
2. 再试挂载到可写目录：`Failed to save truststore ... (Permission denied)`——rootless + userns 下文件属主不匹配。
3. 试 `update-ca-trust extract`：官方镜像精简掉了 p11-kit，报
   `/usr/bin/trust: error while loading shared libraries: libp11-kit.so.0`。
4. 试给容器内 Jad 参数 `KC_HTTPS_TRUST_STORE_FILE`：不对，那是 HTTPS 服务端证书，不是出站信任库。

**最终解决（写进 `docker/keycloak/Containerfile`）**：构建期用 `keytool` 把根 CA 直接导入镜像内置 `cacerts`：
```dockerfile
USER root
COPY tri.local_ca.crt /etc/pki/ca-trust/source/anchors/tri.local_ca.crt
RUN keytool -importcert -noprompt -trustcacerts -alias tri-enterprise-root \
      -file /etc/pki/ca-trust/source/anchors/tri.local_ca.crt \
      -cacerts -storepass changeit
USER 1000
```
运行时零挂载，只读即可。

> 教训：**先把"能不能连 AD"验证掉再往下走**。AD 连不上的话，后面所有组映射、角色、令牌都是白测。

## 3. `start --optimized` 容器无限重启

**现象**：容器反复 `Up 1 second (starting)` → 退出，日志每 3 秒刷：
```
The '--optimized' flag was used for first ever server start.
Please don't use this flag for the first startup or use 'kc.sh build' to build the server first.
```

**解决**：镜像构建期执行一次 `kc.sh build`（构建期选项：`KC_DB`/`KC_CACHE`/`KC_HEALTH_ENABLED`/`KC_METRICS_ENABLED`/`KC_HTTP_ENABLED`/`KC_PROXY_HEADERS`/`KC_HOSTNAME_STRICT`），运行期选项（`KC_DB_URL`/`KC_HOSTNAME` 等）仍在 compose 传入。见 `Containerfile` 第 2 段。

**踩坑补充**：一开始试图 `podman run --rm ... kc.sh build` 后再 `podman commit`，结果镜像层损坏（`ZipException: zip END header not found`）。最后改为在 Dockerfile 里 `RUN kc.sh build` 才稳。

## 4. Keycloak 连不上 AD 的"隐藏原因"：provider.parentId 不是 realm UUID

**现象**：LDAP provider 看起来配置正常，但全量同步报
```
HTTP 400 {"errorMessage":"UnknownError"}
```
日志里：
```
org.keycloak.models.ModelIllegalStateException: Realm with id tri not found
```

**原因**：通过 admin REST API 创建 component 时，如果 `parentId` 写成 realm **名称**（`tri`），
Keycloak 会接受创建，但同步任务用 realm **内部 UUID** 查 realm → 找不到。

**解决**：创建/更新 component 时 `parentId` 必须取 `GET /admin/realms/tri` 返回的 `id`：
```python
st, realm = http("GET", f"/admin/realms/{realm}", token=T)
component["parentId"] = realm["id"]
```
`configure.py` 的 `ensure_ldap()` 已处理；`verify` 子命令第一项就会对比这两个值。

## 5. AD 组映射：三个连环坑

### 5.1 嵌套继承导致同步失败
```
GroupTreeResolver$GroupTreeResolveException:
  Group 'Administrator' referenced as member of group 'Administrators' doesn't exist
```
AD 内建组 `Administrators` 的成员里有一个「已删除/外置」的 Administrator 对象，Keycloak 递归解析组树时崩。

**解决**：`group-ldap-mapper` 的 `preserve.group.inheritance=false`（每个用户按 `memberOf` 直接解析，不推祖先组）。
> 这也符合本企业的实际情况：AD 是扁平的 `OU=Staffs`，嵌套组语义本来就没在用。

### 5.2 组同步了，但用户没挂到组上
**现象**：`keycloak_group` 表有 59 个组，`user_group_membership` 表 **0 行**；用户令牌里没有 `realm_access.roles`。

**原因**：group-ldap-mapper 下用户-组关系是**查询时动态解析**的；角色是按「持久化的用户-组关系」计算的，
所以必须把动态结果**物化**到 Keycloak。

**解决**：`configure.py sync_user_groups()`：
```python
for u in users:
    groups = GET /admin/realms/tri/users/{u.id}/groups     # 动态解析结果
    for g in groups:
        PUT /admin/realms/tri/users/{u.id}/groups/{g.id}   # 幂等物化
```
实测 100 个用户、56 个有组、写入 108 条，耗时 <10 s。执行后令牌里正确出现
`roles=['ts:admin','ts:finance','kb:admin','kb:reviewer','cluster:admin']`。

### 5.3 role-ldap-mapper 会把 AD 全部内建组变角色
**现象**：用 `role-ldap-mapper` 直接映射 AD 组后，realm 里冒出 62 个角色，包括
`Domain Admins`、`Enterprise Read-only Domain Controllers`、`Backup Operators`……

**结论**：不要用 role-ldap-mapper 做业务授权。改用「**AD 组 → Keycloak 组 → 组上挂业务角色**」，
业务角色只有 5 个，治理边界清楚（见部署文档 §1.2）。

## 6. AD 直连搜索超时 / reset（不要再踩）

**现象**：用 Python 直连 LDAPS 执行 `(&(objectClass=user)(memberCategory=person))` 或
`(objectClass=person)` 的子树搜索，服务端只返回 4 个 entry 就 `Connection reset by peer`；
换成无过滤器的搜索则超时。

**结论**：这是 AD 或中间安全设备对本机（172.16.50.101）的限制，**不是代码 bug**。
不要在本机写脚本直连 AD 做大范围搜索。

**正确做法**：用 Keycloak 的 `user-storage/{id}/sync` 与 `users/{id}/groups` 接口（其内部是分页的）。

## 7. rootless podman 下 `bootstrap-admin` 失败

**现象**
```
ERROR: Console is not active, but password is required
```
或（在运行中的容器里执行）
```
ERROR: Unable to start the management interface on 0.0.0.0:9000 ... Address already in use
```

**原因**：Keycloak 26.8 的 `bootstrap-admin` 需要交互式控制台或纯参数；在 rootless + userns 下 tty 传递有问题；
在已运行实例里执行又会占用 9000 端口。

**解决**：用**独立的一次性容器**连同一数据库执行（deploy.sh 的 `ensure_admin`）：
```bash
podman run --rm --network oidc --userns=keep-id \
  -e KC_DB=postgres -e KC_DB_URL=jdbc:postgresql://db:5432/keycloak \
  -e KC_DB_USERNAME=keycloak -e KC_DB_PASSWORD="$POSTGRES_PASSWORD" \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD="$KC_BOOTSTRAP_ADMIN_PASSWORD" \
  -e KC_HTTP_PORT=28080 -e KC_HTTP_MANAGEMENT_PORT=29000 \
  localhost/tri-oidc-keycloak:1.0.0 bootstrap-admin user --no-prompt --optimized \
    --username admin --password:env KC_BOOTSTRAP_ADMIN_PASSWORD
```

**另一个坑**：compose 里忘了传 `KC_BOOTSTRAP_ADMIN_*` 环境变量时，**不会报错**，
只是 master realm 里没有 admin 用户，表现为管理端登录 `invalid_grant`。
检查：`podman exec oidc-db psql -U keycloak -d keycloak -tAc "select username from user_entity"`。

## 8. nginx 502：SELinux 阻止 nginx 连接 127.0.0.1 上的容器端口

**现象**
```
[crit] connect() to 127.0.0.1:18080 failed (13: Permission denied) while connecting to upstream
```

**解决**
```bash
sudo setsebool -P httpd_can_network_connect on
```
`deploy.sh nginx` 已自动执行（检测到 Enforcing 时才做）。

## 9. 登录后立刻 400 `Restart login cookie not found`

**现象**：浏览器（含脚本模拟）拿到登录页后提交账号密码，返回
`Restart login cookie not found. It may have expired; it may have been deleted or cookies are disabled.`

**原因**：两件事叠加——
1. 测试脚本没保存 cookie（或用了不允许「cookie jar 失效」的地方）；
2. 更重要的是：`oidc-verify` client 配置了 `pkce.code.challenge.method=S256`，
   脚本最初的授权请求没带 `code_challenge` / `code_challenge_method`，
   Keycloak 直接回 302 `error=invalid_request&error_description=Missing parameter: code_challenge_method`。

**排查提示**：**用 `curl -v` 看 302 的 Location，不要只看页面 HTML**。Keycloak 的错误常常在重定向 URL 的
`error_description` 里而不是页面正文。

**结论**：脚本里每个授权请求都要带 PKCE；session cookie 必须手工维护（本项目 `verify-oidc.py` 内置了一个最小 Session 类）。

| 问题 | 解决 |
|---|---|

## 11. 其他小坑

| 现象 | 原因 / 解决 |
|---|---|
| `podman build` 报 `COPY tri.local_ca.crt: no such file` | Dockerfile 的 `COPY` 相对于**构建上下文**；上下文设为 `deploy/certs` |
| `podman-compose up` 后容器名一长串自动名仍未创建 | 先 `podman rm -f` 旧容器再 up；compose 1.0.6 改 env 后不会重建已有容器 |
| 改了 `.env`（如新增 bootstrap 变量）后容器没生效 | `podman-compose` 按 config-hash 判重；先 `podman rm -f oidc-kc-1 oidc-kc-2` 再 `up -d` |
| 检查链路时发现 `issuer` 是 `http://kc-1:8080/...` | nginx 没带 `Host`/`X-Forwarded-Proto`；`KC_HOSTNAME` 必须设成 `https://sso.tri.local` |
| 容器内 `ls /etc/pki/ca-trust/...` 权限不够 | 官方镜像以 UID 1000 运行；需要 `--userns=keep-id` + 挂载目录可写（本项目最终改为构建期烤入，无此问题） |
| 从 Mac 用 `tar -C` 打包上传，目标端出现 `._xxx` 文件 | macOS 扩展属性；`tar --no-mac-metadata` 或在目标端 `find . -name '._*' -delete` |

## 14. 知识平台 client 缺 groups scope（2026-11-03）

**现象**：用 `knowledge-hub` client 请求 `scope=openid profile email roles groups` 时，IdP 直接 302 回
`error=invalid_scope&error_description=Invalid scopes: ... roles groups`；
`man-timesheet` 却能正常请求 —— 两个 client 配置不一致。

**原因**：`roles` 在 realm 默认 scope 里（所有 client 都有），`groups` 是**可选 scope**，
只分配给显式需要的 client（工时、验收 client）。知识平台也是"按 AD 组推导角色/部门"的系统，属于漏配。

**解决**：
1. `configure.py` 的 `ensure_groups_scope_assigned()` 的 `clients_needing_groups` 加入 `knowledge-hub`；
2. 执行 `./deploy/deploy.sh provision`（幂等，会补上 optional scope）。

**验证方法**（实机已做）：
- 走完整授权码流程，`access_token.realm_access.roles` 含 `kb:admin / kb:reviewer`；
- `userinfo.groups` 返回 `["Group_AgenticFlow","Group_AllStaffs","Group_BackupEnd","Group_Roots"]`。

> 另一个顺手发现：直接用脚本模拟浏览器登录时，若原样发送 `Origin: https://ai.tri.local`，
> Keycloak 26.8 会报 **invalid_origin**（脚本访问 `/realms/...` 时 Origin 与 `webOrigins` 的匹配是按页面 Origin 算的）。
> 浏览器正常使用不受影响，只是测试脚本要注意别带 Origin 头。
