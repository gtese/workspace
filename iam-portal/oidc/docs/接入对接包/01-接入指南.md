# 01 接入指南（给业务系统开发者）

> 目标读者：负责改造自己系统的**后端工程师**。
> 读完本文能回答：登录怎么走、我必须做什么、哪些事绝对不能做、大概要几天。
> 接口细节见 [02-参数与接口.md](02-参数与接口.md)；验收见 [03-验收清单.md](03-验收清单.md)。

---

## 1. 一分钟理解

改造前，每个系统各自让员工输域账号口令，再拿口令去 AD 验证：

```
员工 ──口令──► 你的系统 ──LDAP bind──► AD
```

改造后，**口令只在 IdP 输入一次**，你的系统只收"已签名的身份声明"：

```
员工 ──口令──► sso.tri.local ──LDAP bind──► AD
                    │ 授权码（一次性、短时效）
                    ▼
               你的系统 ──用授权的 code 换取 ID Token（含 sub/姓名/角色）──► sso.tri.local
```

三个好处（也是你为什么要做）：
1. 员工少输一次口令，已登录其它系统后进来**免登录**；
2. 你的系统**不再接触口令**（安全事故面大幅缩小）；
3. 权限不再依赖 AD 组名字符串，改为 IdP 统一下发的**业务角色**。

## 2. 你必须做的 6 件事（少一件就不算接好）

### ① 删掉口令登录

- 删掉登录页里的账号/密码输入框；
- 删掉 `/login` 的处理逻辑与 LDAP 配置；
- **不要"保留旧的以防万一"**——保留就等于永远保留，且会出现两条都能进的路。
- 切换期可用一个开关 `AUTH_MODE=oidc|ldap` 应急，验收通过后删除。

### ② 发起登录：跳转 IdP

```
GET /auth/login（你自己的路由）
  1. 生成并保存到后端会话：state（随机）、nonce（随机）、code_verifier（随机）
  2. code_challenge = base64url(sha256(code_verifier))
  3. 302 到：
     https://sso.tri.local/realms/tri/protocol/openid-connect/auth
       ?client_id=<你的 clientId>
       &redirect_uri=<你登记的精确回调地址>
       &response_type=code
       &scope=openid profile email roles
       &state=...
       &nonce=...
       &code_challenge=...
       &code_challenge_method=S256
```

⚠️ **必须整页跳转**（`location.href` / 服务端 302）。用 `fetch`/`axios` 调用是拿不到登录页的。

### ③ 回调：换令牌并校验

```
GET /auth/callback?code=...&state=...
  1. 校验 state 与后端保存的一致（一次性，用完即删）。不一致 → 400，不要继续
  2. 后端 POST https://sso.tri.local/realms/tri/protocol/openid-connect/token
       grant_type=authorization_code
       client_id=...、client_secret=...
       code=...、redirect_uri=<与第 ② 步完全相同>
       code_verifier=...
  3. 校验 ID Token：RS256 签名（JWKS）、iss、aud、exp/nbf（容差 60s）、nonce
  4. 建会话（见 ④），302 回原页面
```

### ④ 建你自己的会话

| 规则 | 原因 |
|---|---|
| 用户主键用 **`sub`**（UUID） | 用户名会变（改名/域迁移），`sub` 不变 |
| 姓名/邮箱用 `name` / `email` | 仅用于展示 |
| `preferred_username` 只用于**首次对账** | 迁移时把历史数据按用户名挂到 `sub` |
| 会话 cookie：`Secure; HttpOnly; SameSite=Lax` | 防 XSS 窃取、防 CSRF；Safari 下 `SameSite=None` 反而会被拦 |
| **令牌不进浏览器、不进日志** | access/refresh token 只存在服务端 |
| 不要每个请求都去验 IdP | 本地会话 + 短角色缓存；IdP 短暂故障时既有会话可继续 |

首次登录对账：
```
按 sub 查本地用户 → 有则直接用
                 → 没有：按 preferred_username 找本地用户 → 找到就绑定 sub（记审计）
                 → 都没有：创建新用户
```

### ⑤ 按角色授权

```
# 反例 if (user.groups.includes('Group_Roots'))
# 正例 if (roles.includes('kb:admin'))
```

角色在 `access_token.realm_access.roles`（或 userinfo），**过滤掉内建角色**
（`default-roles-tri`、`offline_access`、`uma_authorization`、`account`），
只认业务角色：`ts:admin`、`ts:finance`、`kb:admin`、`kb:reviewer`、`cluster:admin`。
（你的系统需要什么角色，向 IT 提需求，由 IT 在 `ROLE_MAPPINGS` 里配。）

### ⑥ 登出要走 IdP

```
1. 清本地会话
2. 302 到 https://sso.tri.local/realms/tri/protocol/openid-connect/logout
        ?client_id=...&post_logout_redirect_uri=<你的首页>
```
只清本地 cookie = 其它系统仍然登录着。前端必须**整页跳转**到该地址。

## 3. 你的权限依赖 AD 组怎么办（C 类系统）

如果你的系统除了"管理员/普通用户"还有"部门""项目负责人""财务"等业务岗，
且这些**目前是用 AD 组成员判断的**，那么：

1. 登录时 scope 加 `groups`（`openid profile email roles groups`）；
2. 回调后再调一次 userinfo 取 `groups` 数组（形如 `["Group_AllStaffs","Group_KB_EDA"]`）；
3. 把组数组喂给你**现有的**角色/部门推导函数（不要重写规则），
   并取「AD 组推导结果」与「IdP 角色」的**较高者**，避免切换期有人被降权；
4. 目标态：逐步把判断条件从"组名"换成"IdP 角色"，AD 组只作为过渡。

> 为什么不能直接删掉 AD 组判断：本企业的 AD 是扁平 `OU=Staffs`、没有部门属性，
> 部门边界完全靠 `Group_KB_<KEY>` 这类组表达；直接删会让"部门可见范围"失效。

## 4. 安全红线（评审会逐条对照，任何一条不满足都算未完成）

| # | 红线 | 常见反例 |
|---|---|---|
| 1 | `client_secret` 只在后端 | 写进前端 JS / 移动端包 |
| 2 | 必须校验 `state` | 只校验 code，不校验 state（CSRF 漏洞） |
| 3 | 必须校验 `nonce` | 直接信任 ID Token（重放攻击） |
| 4 | 必须校验 `iss` / `aud` / `exp` | 只验签名就放行 |
| 5 | 必须 PKCE **S256** | 省略 `code_challenge`（IdP 会直接报错） |
| 6 | 回调地址精确匹配 | 用通配/开放重定向 |
| 7 | 会话 cookie `Secure; HttpOnly; SameSite=Lax` | 把令牌放 localStorage |
| 8 | 令牌不进浏览器、不进日志 | 打印 access_token 排障 |
| 9 | 登出必须走 IdP | 只 `clearCookie` |
| 10 | 不保留口令登录旁路 | "为稳妥"两套登录长期并存 |
| 11 | IdP 故障时不"放行" | "IdP 挂了就跳过校验" |
| 12 | 用户主键用 `sub` | 用用户名做主键 |
